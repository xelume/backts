# 应用配置与生命周期

配置请求体上限与监听地址，根据进程所有权选择启动和关闭方式。

先按[创建自己的应用](createApplication.md)准备入口；本页构造和启动示例是替换方案，不应在同一实例上连续启动。

## 应用选项

```ts
const app = createHttpApp({
  maximumBodyBytes: 64 * 1024,
  logger: { format: "pretty", routes: true },
});
```

| 配置 | 默认值 | 用途 |
| --- | --- | --- |
| `maximumBodyBytes` | 16384 | 读取请求体的累计原始字节上限，必须为正整数 |
| `logger` | 内置 pretty 日志 | `false` 静默，或传日志选项与自定义出口 |
| `errorHandler` | 内置错误 JSON | 自定义错误响应 |
| `onError` | 无 | 观察请求异常 |
| `onRequestComplete` | 无 | 观察响应完成或连接提前关闭 |

`createHttpApp(16384)` 仍可用；需要多个选项时优先使用对象形式。

## 启动地址

`run` 和 `listen` 接受相同的地址参数：

```ts
await app.run(3000);                         // localhost
await app.run(3000, true);                   // 0.0.0.0
await app.run({ port: 3000, host: false });   // localhost
await app.run({ port: 3000, host: "127.0.0.1" });
```

端口必须为 1–65535 的整数，不支持端口 0 或端口自动递增。`host` 省略或为 false 时使用 localhost；true 时绑定所有 IPv4 网卡。localhost 的实际地址解析由系统决定，需要固定 IPv4 时明确指定 `127.0.0.1`。

## 选择 run 或 listen

| 方法 | 使用场景 | 启动失败 | 信号和退出 |
| --- | --- | --- | --- |
| `run()` | 独立服务进程入口 | 记录启动失败，退出码 1 | 托管 SIGINT/SIGTERM |
| `listen()` | 嵌入其他进程或自己管理生命周期 | 返回拒绝或在参数校验时抛错 | 不接管信号及进程退出 |
| `close()` | 主动停止应用 | 共享关闭结果 | 不主动退出进程 |

一次应用实例只允许一次启动尝试。首次尝试开始时，路由、中间件和静态挂载被冻结；关闭后不能重新启动该实例。

`close()` 停止接受新连接，关闭空闲连接并等待活动响应；5 秒后销毁剩余连接。重复关闭共享同一个 Promise，未启动时调用无操作。

`run()` 收到关闭信号时调用上述流程。超时强制关闭会以状态码 1 退出；底层关闭未能结束时有第 6 秒兜底。首次信号后 250ms 内的重复转发被合并，之后再次收到信号可立即强制退出。建议每进程只用一个托管 `run()` 应用。

## 显式管理资源

在启动前用 `app.manage()` 注册资源。依赖实例仍由业务创建并注入 Service；框架只调用生命周期回调，不扫描或解析依赖。

```ts
// database 是应用自己的连接适配器，connect/close 由该适配器实现。
app.manage({
  name: "database",
  start: async (): Promise<void> => { await database.connect(); },
  close: async (): Promise<void> => { await database.close(); },
});
```

| 阶段 | 契约 |
| --- | --- |
| 注册 | 名称不能全为空白，应用内按原值区分大小写且唯一；复制名称和回调，启动后禁止注册 |
| 启动 | 按注册顺序等待 start；全部成功后才监听 HTTP |
| 启动失败 | 逆序调用已尝试启动资源的 close，包括抛错的 start 所属资源；后续未启动资源不清理 |
| 监听失败 | 回滚所有已初始化资源；未监听成功的 HTTP 服务无需排空 |
| 正常关闭 | 停止接入并排空 HTTP；有资源时继续等待请求处理函数结束，再逆序等待 close |
| 清理失败 | 记录通用错误并继续清理其余资源，最终 close 拒绝；重复调用共享同一结果，不重复清理 |
| 启动中关闭 | 等待当前 start 返回，然后回滚，不启动后续资源；listen 拒绝，close 等待回滚完成 |

start 失败可能留下部分资源，所以 close 必须能够清理部分初始化状态。启动失败保留原始启动错误，回滚失败另外记录；之后调用 close 仍能获得清理失败。回调不要等待本应用的 listen/run/close，否则会形成互相等待。实例方法请用箭头函数委托，避免依赖回调的 this 绑定。

响应提交或客户端断连不等于请求处理结束。注册资源后，框架等待包含中间件和错误处理在内的请求处理链结束；不等待分离的后台 Promise 或 onRequestComplete 观察回调。应用必须在资源 close 中协调自身后台任务，不能把数据库释放等操作交给完成观察回调。

run 在资源初始化前绑定信号；关闭信号触发完整关闭流程，六秒兜底覆盖初始化等待、HTTP 排空和资源释放。第二次独立信号仍可强制退出，清理失败以状态码 1 退出。强制退出不保证剩余回调完成。

listen/close 不强制退出进程，也没有新增资源回调超时：挂起的 start、处理器或 close 会让关闭持续等待，嵌入方必须管理自己的期限。HTTP 的五秒连接期限仍然有效，但销毁连接不会取消业务函数。回调自身的超时也不等于底层操作已取消。

未注册资源时保持原有 HTTP 关闭行为。Todo 内存仓储没有连接资源，因此不增加空生命周期回调。
