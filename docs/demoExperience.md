# Demo 开发体验评估

本轮以 core 消费者身份完成任务搜索、筛选、分页与单项查询；没有修改 core 公共 API。

## 顺手的部分

- 路由组承接业务异常边界：create/update 不再重复捕获 TodoInputError，业务规则不依赖 HTTP。
- request.queryAll 支持重复参数检测，request query API 能支撑常规分页筛选。
- 全局中间件统一安全响应头，框架默认输出可读日志，可配置 JSON 或自定义出口，无需修改监听循环。
- 明确分工使新增单项查询只涉及 Service、Controller 和路由注册；页面与领域逻辑互不依赖。

## 仍有摩擦

1. 输入解析最繁琐：字符串转整数、重复参数、默认值、枚举和 JSON 字段校验都需手写。后续适合先设计可静态编译的解析函数组合，避免直接引入复杂 schema 库。
2. 响应仍需反复 JSON.stringify。未来可以验证对象响应 API 的编译支持，保留字符串入口兼容；本轮没有为单个业务创建无意义包装层。
3. scriptc 0.0.36 探针仍报 SC2002：仓储类实例不能直接转换为当前函数记录接口。当前 createInMemoryTodoRepository() 已改为闭包直接返回仓储对象，不再需要私有类和兼容委托；调用方仍使用同一仓储契约。
4. 缺少类型化请求状态，之后鉴权身份和请求 ID 传递仍需专门设计；本 demo 不用全局变量模拟请求身份。
5. 当前日志有方法、路径、状态和耗时，没有关联 ID；错误观察默认不输出敏感原始异常。
6. 每次修改后需要编译并重启，开发反馈慢于常见解释执行服务；构建/重启工作流是下一阶段值得改进的体验。

## 验证

pnpm check：37 项原生集成测试通过，包括新增搜索大小写、状态、总数、分页、非法/重复参数、单项查询和响应中间件。原生领域测试覆盖筛选与越界分页，前端通过 node --check。

浏览器实际验证创建、完成切换、状态筛选、空结果、11 条数据分页、第二页和键盘编辑保存。加载结果防过期与失败恢复有实现和代码检查；未宣称已通过自动化断网/慢网络测试。

## 结论

常规 HTTP 业务组织已经比较顺手；主要摩擦集中在输入校验、序列化和编译器兼容，而不是缺少架构层。后续优先验证这些能力的最小公共契约，不应继续增加抽象层以替代真实功能。
